## 1. 目标与本次调整

先把 Demo 的 AI 调用闭环跑通，按接口逐项实现实体提取、图片生成、剧本生成、视频生成，后续扩展分镜、语音、增强与一致性评测。正式业务数据以 LumenX 为准；所有迁入的新 AI 能力由 Prism 实际执行。已有业务进程内调用须逐项切换，不能先删除兼容实现。

v1 的主要修订：

- 不再把项目、角色卡、分镜、候选审批、成片导出视为 Prism 已有模块。
- Prism 可独立保存参考素材、任务输入输出、实验记录及角色描述快照，不需要在 LumenX 注册后才能保存。
- 移除 Prism 正式角色主数据管理、业务审批与项目权限建设任务。
- P1 改为公共任务/媒体底座与按能力拆分的接口开发，不以完整角色卡产品或 18 条视频实验为前置条件。
- 暂不建设统计实验、加权评分、双人盲评、GPU 成本量表；保留接口正确性、文件完整性与一次真实生成的 Demo 检查。
- 模型配置沿用 MongoDB `model_comfigs`；复用现有 MongoDB 实例中的独立库和账号。
- 代码、模型与运行文件在 231 本地 `/data/aigc` 子目录；本机仅开发和管理，不存储权重、不运行模型。

## 3. 职责和数据所有权

### 3.1 LumenX

- 保存正式项目、角色卡、服装版本、画风版本、资产审批、镜头绑定和最终采用的结果。
- 完成用户登录、业务权限检查、项目归属验证。
- 上传输入文件，提交 Prism 异步任务，查询状态，下载生成结果并保存为正式业务资产。
- 用户是否采用候选、是否更新正式角色卡，由 LumenX 决定。

### 3.2 Prism

- 执行剧本生成、实体提取、图片/视频生成等 AI 任务，负责提示词、模型适配、推理调度与结果校验。
- 在独立数据库保存任务输入快照、模型/工作流版本、状态、错误、输出清单和历史；本地保存任务参考文件与生成文件。
- 可以保存独立实验使用的角色描述和参考图，也可以记录 LumenX 传来的角色/服装/风格版本。这是任务输入历史，不与 LumenX 正式角色状态双向同步。
- 不创建业务项目、不决定正式角色当前版本、不替 LumenX 审批资产、不实现项目成员权限。
- 保留服务间 token 鉴权、受控文件访问和路径校验。这些属于服务接口边界，不是业务权限体系。

### 3.3 对“数据库独立”的澄清

用户的判断正确：Prism 的记录存入独立数据库，不会因保存相同角色名称或描述就混入 LumenX。是否存在索引不是跨库混合的决定因素；只有应用显式读取、关联、导入或回写，才发生业务联系。

之前“两套角色版本难同步”的顾虑仅适用于两个系统都维护“正式版本和批准状态”的情形。本方案明确 LumenX 为业务事实来源，Prism 只保存推理及历史，不需要两套正式状态同步。

可选 `source_context` 保存 `source_system`、`project_id`、`shot_id`、`character_id` 等关联信息，仅供追踪，不自动创建业务对象，也不将调用方填写的 ID 当作授权证明。

## 4. 端到端调用流程

```text
LumenX 完成业务鉴权/选择资产
  → 将参考文件上传 Prism，取得 media_id
  → 提交某能力的异步任务，引用 media_id 与输入快照
  → Prism 返回 202 / job_id
  → 独立 worker 领取任务，调用文本服务或 ComfyUI
  → Prism 将结果媒体下载到自身本地目录，写入输出清单
  → LumenX 查询任务，取得结果文本或 download_url
  → LumenX 下载文件并保存正式资产，记录 prism_job_id 便于追踪
```

任务查询不触发新推理。页面与业务接口共用任务服务。初期采用轮询，不把 WebSocket、回调或复杂工作流引擎作为前置依赖。

## 5. 媒体文件方案

### 5.1 输入：文件上传

采用用户建议：LumenX 通过 multipart 文件上传给 Prism → Prism 保存本地 → worker 上传至选定 ComfyUI。跨机器不传“调用方磁盘绝对路径”让服务自行读取，也不要求 Prism 访问业务数据库或挂载业务文件卷。

建议接口（新增，未实现）：

```text
POST /v1/media                     # multipart 文件，返回 media_id / size / mime_type / sha256
GET  /v1/media/{media_id}/download  # 使用服务 token 下载
```

Prism 根据内部媒体记录解析文件，不接受任意磁盘路径。保存时使用服务生成的文件名；原始文件名仅作展示。按类型限制文件大小，检查实际内容类型，拒绝路径穿越。具体限制按图片/音频/视频分别配置。

### 5.2 保存路径与下载

231 运行目录建议为 `/data/aigc/lumenx-prism`，媒体位于其 `data/media`，均不纳入 Git。正式路径在部署时核对；本机仓库不用于模型存储或推理。

```text
data/media/inputs/<media_id>/source.<ext>
data/media/derived/<media_id>/<transform_id>.<ext>
data/media/outputs/<job_id>/<artifact_id>.<ext>
```

worker 通过 ComfyUI 的媒体接口取回结果，不依赖远端容器绝对路径。先写临时文件，成功完成并检查文件可读取后再原子发布最终文件及元数据；多输出任务的必需输出全部就绪才标记 succeeded。

任务 `result.artifacts` 返回 `media_id`、`kind`、`mime_type`、`size_bytes`、`sha256`、`download_url`。下载 URL 由 Prism 的可达服务地址与媒体路由组成，不能把 127.0.0.1 返回给远端 LumenX。凭据放请求头，不放 URL。可达地址属于服务部署配置，不是模型配置。

LumenX 查询成功后下载、保存自己的正式文件。Prism 下载地址用于交付和历史查看，不应成为 LumenX 正式资产的唯一永久位置。传输中断可以重新下载，不重新生成。

### 5.3 为什么记录哈希

SHA256 是文件内容指纹，用来确认“这次任务究竟用了哪一份文件”，以及下载前后内容是否一致。它不是加密，也不能判断角色是否相似。

同名图片被覆盖后哈希会改变；文件换名字但内容未变，哈希保持不变。若图片经过缩放、裁剪或转码，分别记录原始文件和实际提交推理文件的哈希及转换参数，方便追踪差异。没有转换时只需同一份内容记录，不重复复制。

MVP 在上传/落盘时计算 SHA256 即可，不引入复杂去重系统，也不在每次轮询时重复读取大文件计算。

### 5.4 生命周期

新增媒体元数据集合建议为 `ai_media`。记录媒体 ID、相对存储路径、类型、大小、哈希、创建时间及所属任务/来源；禁止把文件二进制塞进任务文档。

Demo 阶段不自动删除历史媒体，记录磁盘占用并在空间不足时明确拒绝新写入。后续再加入保留期限、下载确认和清理策略。MongoDB 记录过期与磁盘删除必须协同，不能仅加 TTL 索引后留下失联文件。

## 6. 异步任务与 worker 改造

### 6.1 通用契约

保留已有 `queued → running → succeeded/failed` 状态与旧实体提取响应兼容性，通过 `phase` 表达 preparing、uploading、submitted、inference、downloading、finalizing 等细节。

新增任务公共字段：`type`、`schema_version`、`source_context`、输入与参考快照、模型配置 ID/版本、工作流版本、上游实例及任务 ID、输出清单。外部响应使用明确字段白名单，内部连接信息、凭据及磁盘路径不随新增字段自动公开。

各能力有独立请求 schema 和提交接口，统一使用 `GET /v1/jobs/{id}` 查询；列表增加可选 type 筛选。保留实体提取的同步兼容接口。

继续使用 Idempotency-Key。已有实体提取键语义不变；通用提交指纹应包括任务类型、输入和有序媒体引用，防止不同能力相同正文被误判为同一提交。同键不同内容返回 409，不自动重新生成。

### 6.2 Handler 注册

将 Worker 中实体提取专用逻辑提取为 EntityExtractionHandler，再增加 ImageGenerationHandler、ScriptGenerationHandler、VideoGenerationHandler，后续扩展分镜与语音。worker 按其支持的类型领取，不领取未知类型后再报错。

公共层负责领取、续租、状态与审计；handler 负责输入准备、模型调用、结果处理。文本任务继续使用现有无自动推理重试策略。外层仍可用同步轮询进程，不必为了“接口异步”把所有 Python 函数改成 async。

### 6.3 ComfyUI 恢复与不确定结果

- 提交前持久化执行意图及关联标识；收到响应后保存 provider_instance_id 和 prompt_id。
- worker 重启时，已知 prompt_id 的任务先查询上游队列/历史并继续回收结果，不重新提交。
- 提交成功但响应丢失/写库失败：优先依据持久化关联标识检查上游；无法唯一确认时标记 execution_outcome_unknown，禁止自动重发。
- 下载或结果写库失败只重试对应步骤，不重新生成。
- 已有 recover_expired 逻辑必须按任务类型区分；保留文本任务过期结果未知的语义，视频任务进入恢复查询流程。
- 完成写入仍需匹配有效领取令牌，旧 worker 不能覆盖新持有者结果。
- 首期不承诺端到端 exactly-once，不提供未经验证的通用取消接口；不得用全局中断影响其他调用方的任务。

### 6.4 GPU 容量

初期对共享同一物理 GPU 的图片/视频任务设置一个资源槽，不按 ComfyUI 端口分别计容量。跨 worker 使用持久化资源租约；worker 失联后先核对上游任务是否仍运行，再决定释放资源，不能仅凭本地租约过期立即再投一个任务。

其他程序也可能使用该 GPU，因此容量槽仅约束 Prism 自己的提交；不能宣称能管住所有外部任务。提交前检查服务与队列，冲突时排队或明确返回资源不可用，不停其他服务、不额外启动 ComfyUI 抢资源。文本服务与 GPU 任务可由不同能力集合的 worker 执行，避免视频长期阻塞文本任务。

## 7. 模型配置与工作流

沿用 `model_comfigs` 和 revision 乐观锁，不新增模型环境变量回退。复用 kind、provider、protocol、model、base_url、parameters、capabilities 等字段；首期 ComfyUI 可采用现有 custom_http 协议并以 provider 区分，具体 handler 验证能力专属参数。

扩展用途绑定：图片生成、剧本生成、视频生成；具体字段命名在实施时保持与当前绑定文档一致。当前 entity_extraction_id 行为不变。

区分三类信息：

1. 模型配置：模型、协议、参数、凭据，来自 model_comfigs。
2. 推理实例：服务地址、资源组、启用状态；多模型共享实例时使用显式 instance_id，避免重复设置不同 GPU 容量。
3. 工作流：固定版本的 JSON/模板、哈希及输入映射，保存在代码/部署工件中，由模型配置引用。

任务提交冻结无密钥参数和配置版本，执行时读取凭据并检查版本、启用状态。MVP 延续配置修改后旧排队任务明确失败的行为，不静默换模型；未来若支持历史版本执行另行设计。

## 8. 按能力提供接口

以下除实体提取与通用查询外，均为建议新增契约，不代表已实现。

| 能力 | 提交接口 | 输入核心 | 输出核心 |
|---|---|---|---|
| 实体提取 | POST /v1/scripts/extract-entities/jobs | 剧本、自定义提示词 | characters / scenes / props |
| 图片生成 | POST /v1/images/generate/jobs | prompt、尺寸、可选参考 media_id | 图片 artifacts |
| 剧本生成 | POST /v1/scripts/generate/jobs | 创作简报、风格、长度等约束 | 剧本文本；结构化格式按独立 schema 定义 |
| 视频生成 | POST /v1/videos/generate/jobs | prompt、route、时长、有序参考或首尾帧 | 视频及实际产生的音频 artifacts |
| 分镜规划（后续） | POST /v1/storyboards/generate/jobs | 剧本、角色/风格快照 | 结构化镜头建议，不写业务镜头 |
| 语音生成（后续） | POST /v1/audio/generate/jobs | 文本、声音参数、可选参考音频 | 音频 artifacts |

全部新增提交返回 202、job_id 对应任务文档和 Location；沿用现有任务 API 的 id 字段命名。文本结果直接放任务 result，媒体结果放 artifacts。各能力固定输出 schema，不用一个任意 JSON 接口承载所有功能。

参考图只在具体工作流支持时接受；首期 Qwen 文生图能力不因公共接口有 references 字段就被宣称支持图生图。视频同理，不支持的 route 或参考类型在调用 GPU 前失败。

## 9. H3 一致性能力保留范围

本节是后续实现约束，不是本轮对外部 H3 资料、已部署权重或节点能力的验证结论。v1 §17 原始来源保留作后续核查目录；实现前读取原始材料、固定版本，不直接把 v1 样例当生产契约。

保留：

- 冻结角色、服装、风格及媒体版本快照；上游正式资产更新不改变历史任务。
- ConsistencyResolver 进行确定性引用解析，不依赖 LLM 猜测业务资产关系。
- 引用标签、媒体顺序和实际上传附件一致；保存转换后的真实输入记录。
- 按部署验证结果分别支持 Ref2VA、FL2VA；提示词、权重和工作流不能混用。
- 提示词格式只是软约束，不宣称 fully_preserved 等文字能硬锁身份。
- 保留失败任务、错误阶段及可用中间工件，不只保存成功案例。

不要求 LumenX 的角色快照包含不变的全局服装：服装随镜头选择具体版本；身份特征与服装约束分开记录。多角色使用逐角色绑定，不能只用一个全局 wardrobe_id。

Prism 测试页面可上传参考图、编辑任务级角色描述、选择生成路线并预览输出；不提供“发布正式角色版本”或“批准业务资产”功能。H3 Context-IR、3D Animation Short Generator 编排和社区 Multishot 放入后续研究，不作为 Demo 前置依赖。

P1-E 在 P1-A 完成后即可独立推进，不依赖 GPU。P1-D/F 依赖 P1-B/C；任一路线被环境阻塞时及时报告，不用另一模型冒名通过。已有实体提取作为回归基线，不重写第二套实现。

P1-G 修改业务项目之前说明具体文件、原因和影响；本次方案修订没有授权立即部署或切换现有业务调用。真正切换时按能力逐项进行，保留其他兼容调用。所有阶段默认保留未提交改动供用户审阅。

## 11. Demo 检查与后续评测的区别

本阶段只检查闭环：能提交、能排队、能看到真实状态、能成功或明确失败、能取回文本/文件、能追踪输入和工作流、能在重启后避免盲目重复生成。保留必要的模拟 provider 回归、任务故障恢复和媒体传输测试。

真实联调可按用户已有授权使用已配置付费模型，无需把“免费测试”作为限制。每次以跑通接口所需的小量调用为单位；不因单次失败自动重复批量生成。

暂不执行 v1 的 A/B/C 18 条主实验、加权评分、显著性分析或角色质量通过率。先跑 Demo 并人工查看结果，系统可用不等于角色一致性已验收。后续用户需要质量优化时再制定样本和指标。
